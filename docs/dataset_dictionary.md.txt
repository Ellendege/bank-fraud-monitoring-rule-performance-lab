# Dataset Dictionary

## 1. transactions
**Purpose:** Stores individual customer financial transactions that can later be analyzed for fraud trends, suspicious patterns, alert generation, and confirmed fraud losses.

| Column Name | Meaning | Why It Matters |
|---|---|---|
| transaction_id | Unique ID for each transaction | Primary key for tracking each transaction uniquely |
| customer_id | Unique ID for the customer | Helps link transactions to customer profiles and segments |
| account_id | Unique ID for the account used | Helps analyze account-level fraud patterns |
| transaction_date | Date the transaction happened | Needed for trend analysis, daily monitoring, and reporting |
| transaction_time | Time the transaction happened | Helps identify suspicious timing patterns like late-night fraud |
| amount | Value of the transaction | Critical for fraud exposure, loss analysis, and threshold rules |
| channel | Where the transaction happened (ATM, card, mobile app, internet banking, branch, agent banking) | Helps identify the riskiest channels |
| transaction_type | Type of transaction (cash withdrawal, transfer, payment, deposit, purchase) | Helps group fraud patterns by activity type |
| merchant_category | Type of merchant or business involved | Useful for spotting risky merchant categories |
| destination_account | Account receiving funds | Helps identify mule accounts and suspicious destinations |
| destination_bank | Bank receiving funds | Useful in external transfer fraud analysis |
| country | Country where transaction occurred | Helps identify cross-border or unusual location risk |
| device_id | Device used for the transaction | Useful for detecting repeated suspicious device usage |
| ip_address | IP address used | Helps with digital fraud analysis and geolocation patterns |
| is_international | Indicates whether the transaction was international | Useful for foreign transaction risk monitoring |
| is_high_risk_country | Indicates whether country is considered high risk | Useful for sanctions or risk-based rule logic |
| transaction_status | Final status of transaction (approved, declined, reversed, pending) | Helps separate attempted versus completed activity |

## 2. alerts
**Purpose:** Stores fraud alerts generated by detection rules when transactions or customer activity match suspicious conditions. This table helps measure alert volumes, rule performance, and operational workload.

| Column Name | Meaning | Why It Matters |
|---|---|---|
| alert_id | Unique ID for each alert | Primary key for tracking each alert uniquely |
| transaction_id | ID of the transaction linked to the alert | Connects the alert back to the underlying transaction |
| customer_id | ID of the customer linked to the alert | Helps analyze alert volumes by customer and segment |
| rule_id | ID of the rule that triggered the alert | Critical for rule performance analysis |
| alert_date | Date the alert was created | Useful for alert trend monitoring and daily reporting |
| alert_status | Current status of the alert (new, in review, closed, escalated) | Helps track workflow and alert handling progress |
| alert_priority | Priority level of the alert (high, medium, low) | Helps with triage and queue management |
| queue_name | Investigation queue or team the alert was sent to | Useful for workload and routing analysis |
| assigned_investigator | Name or ID of the person handling the alert | Helps measure operational burden and investigator workload |

## 3. rules
**Purpose:** Stores information about fraud detection rules used to generate alerts. This table helps explain what each rule is meant to detect and supports rule effectiveness analysis.

| Column Name | Meaning | Why It Matters |
|---|---|---|
| rule_id | Unique ID for each fraud rule | Primary key for tracking each rule uniquely |
| rule_name | Name of the rule | Helps identify the rule in reports and dashboards |
| rule_category | Type of fraud pattern the rule targets | Helps group rules into categories like velocity, geography, amount, account takeover, or mule activity |
| rule_description | Short explanation of what the rule is checking | Helps business users understand the rule logic |
| threshold_logic | The trigger condition or threshold behind the rule | Useful for tuning and explaining why alerts are generated |
| channel | Channel the rule applies to | Helps analyze rule performance by channel |
| active_flag | Indicates whether the rule is currently active | Helps distinguish live rules from inactive or retired ones |

## 4. cases
**Purpose:** Stores investigation outcomes for alerts that were reviewed by the fraud operations team. This table helps measure confirmed fraud, losses, recoveries, and investigation performance.

| Column Name | Meaning | Why It Matters |
|---|---|---|
| case_id | Unique ID for each fraud case | Primary key for tracking each investigation case uniquely |
| alert_id | ID of the alert linked to the case | Connects the case back to the alert that triggered investigation |
| investigator_name | Name or ID of the investigator handling the case | Helps measure investigator workload and performance |
| case_open_date | Date the case was opened | Helps track investigation volume and age of cases |
| case_close_date | Date the case was closed | Needed for turnaround time analysis |
| disposition | Final case outcome (confirmed fraud, false positive, customer error, insufficient evidence) | Helps separate real fraud from noise |
| confirmed_fraud_flag | Indicates whether fraud was confirmed | Critical for fraud rate and rule effectiveness analysis |
| confirmed_loss_amount | Value confirmed as fraud loss | Helps measure true fraud impact |
| recovery_amount | Amount recovered after fraud occurred | Helps measure net fraud exposure and recovery performance |
| closure_reason | Explanation for why the case was closed | Useful for root-cause analysis and control improvement |

## 5. customers
**Purpose:** Stores customer-level information used for fraud segmentation, risk profiling, and trend analysis across different customer groups.

| Column Name | Meaning | Why It Matters |
|---|---|---|
| customer_id | Unique ID for each customer | Primary key for tracking each customer uniquely and linking to other tables |
| customer_segment | Group the customer belongs to (retail, SME, corporate, premium, agent) | Helps compare fraud patterns across segments |
| onboarding_date | Date the customer joined the bank | Useful for analyzing fraud among new versus older customers |
| customer_type | Type of customer (individual or business) | Helps identify whether fraud differs by customer type |
| age_band | Age group of the customer | Useful for demographic fraud pattern analysis |
| region | Geographic area where the customer is based | Helps identify regional fraud concentrations |
| risk_rating | Internal customer risk level (low, medium, high) | Useful for risk-based analysis and control design |
